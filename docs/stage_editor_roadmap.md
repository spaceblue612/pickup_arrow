# Arrow 스테이지 제작 도구 — 전체 단계별 진행 문서

작성 기준: 2026-10-19 / 전체 범위: 총 6단계

현재 위치: 권장안을 초기 구현 기준으로 채택하고, 3단계 앱 기반과 4·5단계의 확실한 편집·저장·분석 흐름을 먼저 연결한 첫 실행 버전입니다. 2026-10-20 현재 Ubuntu에서 앱 전용 AppArmor 설정 후 샌드박스를 유지한 기본 실행을 검증했습니다. 고급 생성·게임 반영은 미완료입니다.

최신 산출물: [첫 실제 구현 기록](stage_editor_first_build.md), [실행 안내](../tool/README.md), [실제 앱 화면](design/arrow-editor-first-build.png).

## 1. 최종 목표와 종료 지점

독립 데스크톱 제작 도구에서 스테이지를 열고, 생성하거나 수정하고, 실제 게임 규칙으로 검증한 뒤 저장하여 게임에 반영할 수 있게 만듭니다. 게임과 도구는 하나의 Godot 규칙 코어를 사용합니다.

- **5단계 완료:** 주 개발환경인 Ubuntu/Linux에서 실제 스테이지 제작과 게임 반영이 가능한 첫 사용 버전입니다.
- **6단계 완료:** 로컬 제작으로 운영 원본을 전환하고 Windows·Ubuntu/Linux·macOS에서 같은 데이터와 판정을 재현하는 최종 전환 완료입니다.

이번 전환의 최종 범위에는 기본 편집, 기존 배치를 유지하는 영역·부분 생성, 생성량과 맞물림·연쇄·제거 가능한 수의 제어, 풀이 확인, 설명 가능한 분석 지표, 저장·다시 열기, 게임 반영, 세 운영체제의 실행 확인이 포함됩니다. 화면·제약의 상세 의미·세부 조작은 2단계에서 확정합니다.

체감 난이도 점수의 최종 보정, 대량 자동 생성, 상시 코어 프로세스, 클라우드·협업 기능, Git 자동 조작, 별도 서버, 공개 앱스토어 배포와 서명·공증 자동화는 이번 6단계의 필수 완료 범위에 포함하지 않습니다. 필요하면 별도 작업으로 추가합니다.

## 2. 전체 진행표

| 단계 | 목적 | 상태 | 완료 시 얻는 결과 |
|---|---|---|---|
| 1 | 공용 코어 최소 분리와 JSON CLI | 구현 완료 | 화면 없이 기존 게임과 같은 검증·행동 판정 실행 |
| 2 | 제작 도구 기획과 데이터 흐름 확정 | 기본안 채택 / 모호한 세부 기준은 후속 | 만들 기능·화면·저장·게임 반영 방식의 구현 기준 |
| 3 | Electron 개발환경과 최소 연결 | 기반 구현 / 현재 Ubuntu 샌드박스 실행 검증 | 독립 앱에서 파일을 열고 Godot 코어 호출 |
| 4 | 기존 생성·풀이·분석 기능 연결과 안정화 | 기본 분석·재생 연결 / 생성 미연결 | 도구에서 맵 생성, 클리어 가능성·지표 확인 |
| 5 | 보드 편집·저장·게임 반영 | 수동 편집·후보 저장 초기 구현 / 게임 반영 미완료 | 실제 스테이지 제작과 게임 플레이가 이어지는 첫 사용 버전 |
| 6 | 로컬 운영 전환과 세 운영체제 검증 | 대기 | 기존 제작 흐름을 대체할 수 있는 최종 전환 버전 |

1단계의 기존 테스트 실패 2개는 아래에 별도로 기록합니다. 1단계 기능 완료와 전체 테스트 통과를 같은 의미로 사용하지 않습니다.

원본 handoff의 Phase 0 조사는 1단계의 선행 조사에 포함했습니다. 원본 Phase 2는 현재 3단계, Phase 3은 현재 4단계, Phase 4는 현재 4~5단계, Phase 5는 현재 6단계에 대응합니다. 이후 진행 보고는 이 문서의 **1~6단계 번호**를 사용합니다.

## 3. 단계별 범위와 완료 조건

### 1단계 — 공용 코어 최소 분리와 JSON CLI

**목적:** 도구를 만들기 전에 실제 게임 규칙을 외부에서 호출할 수 있는 기반을 확보합니다.

완료한 작업:

- [x] Godot 4.7.1 개발환경, 기존 구조·데이터·테스트 조사.
- [x] 게임 데이터 검증과 생성 목표 검사 분리.
- [x] 게임·분석기·생성기의 최종 막힘 판정 공통화.
- [x] JSON 좌표 변환과 `validate_stage`, `apply_action` 추가.
- [x] 실제 프로세스 호출과 게임 상태 전환의 일치성 테스트.
- [x] 실행 예제, 오류·종료 코드, JSON 계약 문서화.

완료 조건은 화면 없이 요청 파일 하나로 판정 결과를 얻고, 기존 게임의 판정과 일치하는 것입니다. 이 조건은 충족했습니다.

검증 기록은 Godot 16개 스위트 중 14개 통과, Sheets Node.js 테스트 3개 통과입니다. 필수 4개와 신규 3개 Godot 스위트는 모두 통과했습니다.

산출물과 상세 검증: [공용 코어와 JSON CLI](core_bridge.md).

Electron 환경, 편집 화면, 정식 완성 맵 저장소, 생성·분석용 CLI는 아직 구현하지 않았습니다. `BoardState`의 ID 로딩·스테이지 진행에는 기존 `StageCatalog` 의존성이 남아 있습니다.

### 2단계 — 제작 도구 기획과 데이터 흐름 확정

**목적:** 다음 구현이 화면이나 저장 정책을 임의로 결정하지 않도록 첫 사용 버전의 범위를 확정합니다.

작업 범위:

- 기존 생성 설정과 분석 지표를 조사해 도구의 최소 기능을 정합니다.
- 열기 → 생성/수정 → 검증·풀이 확인 → 저장 → 게임 반영의 흐름을 정합니다.
- 보드 작업 공간, 생성 옵션, 분석 결과, 오류 표시의 기본 화면과 조작을 정합니다.
- 생성 설정, 편집 중인 초안, 확정된 완성 맵, 분석 결과의 역할과 저장 관계를 정합니다.
- 스테이지 ID·순서, 파일 경로·버전, 기존 schema v3 설정 가져오기, 게임 로딩 방식을 정합니다.
- 기존 고정 seed·무작위 생성 모드를 새 저장 흐름에서 어떻게 지원할지 정합니다.
- 4단계에서 처리할 기존 생성 문제의 기대 동작과 인수 기준을 확인합니다.

이 단계에서는 상세 기획과 계약 문서를 작성합니다. 전체 편집 화면을 구현하지 않습니다.

와이어프레임은 기능 구성의 기준으로만 사용하며 외관은 [별도 시각 디자인](stage_editor_visual_design.md)을 따릅니다. 사용자는 Discord 지침에 따른 v0.10을 현재 외관 기준으로 승인했고, Figma v0.9는 비교용입니다. 난이도 지표의 단위·계산식, 편집 조작, 저장·게임 반영 등 미정 계약은 남아 있으므로 외관 채택을 2단계 완료나 전체 구현 착수로 해석하지 않습니다.

사용자 확인이 필요한 결정은 보드 편집 방식, 첫 버전에 노출할 생성 옵션, 저장·게임 반영 절차, 고정·무작위 모드의 최종 역할입니다. 기존 코드에서 확인 가능한 사실은 먼저 조사하고, 기능이나 운영 방식이 달라지는 선택만 확인합니다.

완료 조건:

- 최소 화면과 실제 제작 시나리오가 확정되어 있습니다.
- 3~5단계에서 구현할 필수 기능과 제외 기능이 구분되어 있습니다.
- 생성 설정과 완성 맵을 혼동하지 않는 데이터 계약이 있습니다.
- 저장한 맵을 게임에서 재현하는 로딩 경로와 검증 방법이 정해져 있습니다.
- 사용자 판단이 필요한 주요 선택이 해결되어 있습니다.

산출물: 제작 도구 기능 명세, 기본 화면 구성, 데이터·게임 반영 계약. 실제 저장 형식의 구현은 이후 단계에서 진행합니다.

최근 화면 요청은 보드와 세 조건 요약을 한 화면에 두고 상세 설정만 팝업으로 분리하는 것입니다. [v0.8 목업](wireframes/11-workspace-v08.html)에 스테이지 1~N 목록과 순번·추가·복제·순서 변경의 진입점도 포함했습니다. 화면 조작은 아직 기획 목업이며 실제 스테이지 관리 구현은 아닙니다.

진행 기록: [2단계 기획과 와이어프레임](stage_editor_design.md). 사용자와 질문·토론으로 작업 흐름을 정하고, 와이어프레임을 검토하며 구체화합니다.

현재 확정 사항: 중앙 보드에서 생성·편집 후 사용자가 후보를 저장합니다. 같은 후보의 후속 작업은 그 후보 내부의 저장 이력으로 누적하고, 명시적인 ‘새 후보로 저장’으로만 분기합니다. 2026-10-20 논의에서 기존 배치를 유지한 부분·영역 생성, 퍼센트·개수에 의한 생성량, 맞물림·연쇄 제어와 맵 수치 분석도 필수로 확인했습니다. ‘풀이 가능 개수’는 현재 바로 제거 가능한 화살표 수입니다. 이후 논의는 통합 점수가 아닌 풀이 가능 수·연쇄·영역 개방의 목표·빈도·커버리지를 맵별 속성으로 보존하는 방향으로 정리했습니다. 직접 지정·스테이지별 자동 조정의 단위와 공식, 역할별 판정 기준은 미확정입니다. [통합 정리와 세 화면 목업 v0.7](stage_editor_difficulty_profile.md)에서 현재 상태와 풀이 흐름의 분석을 구분합니다. 확정안·게임 반영 정책도 미확정입니다.

### 3단계 — Electron 개발환경과 최소 연결

**목적:** Godot 게임과 창·레이아웃을 공유하지 않는 독립 도구를 실행합니다.

작업 범위:

- 동일 저장소의 `tool/`에 Electron·React·TypeScript 개발환경을 구성합니다.
- main → 제한된 preload IPC → renderer의 역할을 분리합니다.
- Godot 실행 파일과 프로젝트 경로를 앱 로컬 설정으로 관리합니다.
- 파일 선택, 보드 기본 표시, 검증 실행, 결과·오류 표시를 연결합니다.
- main에서 인자 배열로 Godot를 실행하고 요청별 임시 파일·로그를 관리합니다.
- 시간 제한, 취소, 종료 코드, 잘못된 응답, 설정 오류를 처리합니다.

완료 조건:

- Ubuntu/Linux에서 독립 앱을 실행할 수 있습니다.
- 기존 JSON 예제를 열어 검증·행동 결과를 확인할 수 있습니다.
- 없는 Godot 경로, 한글·공백 경로, 취소·실패 상황이 처리됩니다.
- renderer에 Node 전체 권한을 제공하지 않습니다.
- 기존 Godot 게임과 필수 회귀 테스트가 유지됩니다.

산출물: 실행 가능한 최소 도구, 로컬 설정, 프로세스 호출·IPC 테스트, 개발 실행 안내.

### 4단계 — 생성·풀이·분석 연결과 안정화

**목적:** 이미 있는 생성기와 분석기를 도구에서 사용하고, 결과의 신뢰성을 확보합니다.

작업 범위:

- 기존 GDScript 생성기를 JSON 호출로 노출하고 2단계에서 정한 옵션을 연결합니다.
- 기존 화살표를 보존하는 부분·영역 생성을 확장하고 선택 범위의 점유율·추가 화살표 수로 생성량을 제어합니다. 현재 생성기는 기존 화살표를 유지하는 입력이 없으므로 API 연결만으로 완료 처리하지 않습니다.
- seed와 설정을 보존하여 같은 후보를 재현할 수 있게 합니다.
- 규칙 유효성, 생성 목표 달성 여부, 클리어 가능성을 별도 결과로 표시합니다.
- 기존 풀이 순서를 실제 공용 규칙으로 확인하고 근거를 반환합니다.
- 화살표 수·점유율·굴곡·의존 깊이·제거 가능 선택지 등 기존 지표를 연결합니다.
- 2단계에서 확정한 맞물림·연쇄·현재 제거 가능한 수의 제어를 구현하고, 목표와 실측·목표 미달·분석 시점을 구분합니다. 역할 중심 제어는 2단계에서 채택한 범위로 연결합니다.
- 풀이 결과를 `solved`, `unsolvable`, `unknown`으로 구분하고 제한·실패를 구별합니다.
- 기존 대형 생성 관련 실패 2개의 원인을 해결하고 회귀 검증합니다.

새 충돌 엔진이나 범용 탐색 Solver를 처음부터 재작성하지 않습니다. 현재 제거 규칙의 성질을 이용하는 기존 풀이 방식을 우선 사용하고, 측정 모델·지표의 의미를 문서화합니다.

완료 조건:

- 도구에서 기존 옵션으로 맵을 생성하고 판정·지표를 확인할 수 있습니다.
- 동일 설정·seed의 재현성과 생성 맵 풀이의 합법성이 검증됩니다.
- 기존 화살표를 바꾸지 않고 반복 추가할 수 있으며, 요청한 추가 수·점유율과 실제 결과를 일관되게 표시합니다.
- 새 화살표가 생성 영역을 벗어나지 않으며, 영역 밖의 방해 관계를 포함해 현재 제거 가능한 수와 막힌 수를 집계합니다.
- 생성 제약의 달성 여부와 현재 맵의 수치가 구분되고, 기존·신규 및 영역 간 관계를 근거로 확인할 수 있습니다.
- 생성 목표 미달과 해결 불가, 계산 제한이 구분됩니다.
- 기존 대형 생성 실패 2개가 원인과 근거를 갖고 해소됩니다.
- 난이도 지표가 체감 난이도 확정 점수로 표시되지 않습니다.

산출물: 생성·분석 API, 도구의 옵션·결과 화면, 풀이·지표 테스트, 기존 실패 해결 기록.

### 5단계 — 보드 편집·저장·게임 반영

**목적:** 도구를 실제 스테이지 제작에 사용할 수 있게 합니다.

작업 범위:

- 넓은 보드 작업 공간과 확대·축소·이동을 구현합니다.
- 화살표 생성·수정·삭제, 방향·몸체·배치 금지 영역 편집을 구현합니다.
- 초안의 오류 위치와 수정 결과를 공용 코어로 확인합니다.
- 풀이 순서 재생, 방해 관계, 분석 지표를 보드와 연결합니다.
- 2단계에서 정한 생성 설정·완성 맵 저장과 다시 열기를 구현합니다.
- 기존 schema v3 설정을 가져오고, 기존 ID·순서를 보존하며 게임 로딩에 연결합니다.
- 기존 데이터와 새 데이터를 함께 사용하는 이행 기간의 충돌·실패 처리를 구현합니다.
- 확정된 고정·무작위 모드 정책에 맞춰 런타임 로딩과 생성·분석 의존성을 정리합니다.

완료 조건:

- 생성한 맵을 수정하고 검증한 뒤 저장할 수 있습니다.
- 영역·생성량·제약을 설정하고 결과의 수치와 전체 맵 변화를 확인하면서 부분 작업을 이어갈 수 있습니다.
- 기존 배치를 유지하며 부분 자동 생성·수동 배치를 반복하고 같은 후보에 저장·재개하거나 명시적으로 분기할 수 있습니다.
- 저장 후 다시 열어도 좌표·ID·몸체·설정이 보존됩니다.
- 도구에서 확인한 완성 맵이 게임에서 같은 보드로 로딩되고 같은 풀이로 클리어됩니다.
- 잘못된 데이터나 저장 실패가 정상 데이터를 덮어쓰지 않습니다.
- 기존 게임의 입력·애니메이션·스테이지 진행이 유지됩니다.

산출물: Ubuntu/Linux에서 사용할 첫 제작 버전, 정식 저장·로딩 경로, 게임 연동 회귀 테스트.

이 단계까지가 **실제 제작에 쓸 수 있는 첫 사용 버전**의 종료 지점입니다. 세 운영체제의 지원 완료나 기존 도구 폐기 완료를 의미하지는 않습니다.

### 6단계 — 로컬 운영 전환과 세 운영체제 검증

**목적:** 새 도구로 제작 흐름을 이전하고 전체 전환을 마무리합니다.

작업 범위:

- Google Sheets 원본을 로컬 제작 데이터로 가져오고 결과를 대조합니다.
- 생성 설정과 완성 맵의 운영 원본을 게임 프로젝트가 사용하는 로컬 데이터로 통일합니다.
- 이행 전 데이터를 보존하고 기존 운영 방식으로 돌아갈 절차를 확인합니다.
- 새 도구의 기능 대체가 확인된 뒤 기존 Godot 미리보기·Sheets 의존 기능의 유지 또는 제거를 결정합니다.
- Windows·Ubuntu/Linux·macOS에서 실행, 경로·한글·공백, 설정, Godot 호출, 저장·다시 열기를 확인합니다.
- 같은 샘플 맵에서 검증·풀이·게임 판정 결과를 비교합니다.
- 내부 사용을 위한 OS별 실행·배포 산출물과 설치·실행 안내를 준비합니다.

기본 배포 방식은 Godot 별도 설치와 앱 로컬 경로 설정입니다. Godot 동봉이나 공개 배포용 서명·공증은 별도 요구가 생기면 범위를 정합니다.

완료 조건:

- 새 도구만으로 생성/편집 → 검증 → 저장 → 게임 반영이 가능합니다.
- Google Sheets에 연결하지 않아도 일상적인 스테이지 제작이 가능합니다.
- 세 운영체제의 실기 검증 기록과 재현 가능한 실행 안내가 있습니다.
- 이전 데이터가 보존되고 운영 전환·복구 절차가 검증되어 있습니다.
- 남은 결함과 지원 범위가 문서화되어 있으며 필수 테스트에 미해결 실패가 없습니다.

산출물: 최종 전환 버전, OS별 확인표, 로컬 운영 안내, 데이터 이전·복구 기록.

세 운영체제 중 확인하지 못한 환경이 있다면 해당 항목을 미완료로 남깁니다. 한 환경의 성공으로 전체 지원 완료를 선언하지 않습니다.

## 4. 기존 문제와 처리 단계

| 문제 | 확인된 상태 | 처리 시점 |
|---|---|---|
| STAGE-010 생성 시간·의존 관계 목표 | 변경 전후 약 41초로 10초 기준 초과, 목표 미달 | 2단계에서 기대 동작 확인, 4단계에서 원인 해결 |
| 대형 보드의 첫 후보·기본 seed 기대 | 12×12·15×15 모두 두 번째 후보 선택, 변경 전 상태에서도 동일 실패 | 2단계에서 계약 확인, 4단계에서 원인 해결 |
| 완성 맵 저장·게임 로딩 체계 부재 | 현재 JSON은 생성 설정이며 실행 시 맵 생성 | 2단계 계약 확정, 5단계 구현 |
| 런타임의 카탈로그·생성 코드 의존 | 최소 책임 분리만 완료 | 2단계 모드 정책에 따라 5단계에서 정리 |

기존 실패 2개는 현재 핵심 CLI 기능을 막지 않으므로 2~3단계 진행을 막는 조건으로 두지 않습니다. 다만 4단계 완료 전에 해소하고, 실패를 그대로 둔 채 최종 전환 완료로 처리하지 않습니다. 테스트 기대치 변경이 필요하면 원인·의도한 동작·영향을 제시하고 판단을 요청합니다.

## 5. 진행·범위 관리 기준

- 기본은 단계 순서이며, 사용자가 ‘권장안으로 구현하고 모호한 내용은 다음 개발로 남겨 확실한 것부터’ 요청함에 따라 첫 구현은 3단계 기반과 4·5단계의 최소 사용 흐름을 함께 확인합니다. 일부 기능 구현을 해당 단계 전체 완료로 처리하지 않습니다.
- 이 문서는 현재 저장소를 반영한 진행 기준입니다. 원본 handoff는 설계 배경으로 보존하고, 최신 사용자 지시가 문서보다 우선합니다.
- 2단계에서는 상세 기획을 확정하되 총 6단계와 최종 종료 지점을 기준으로 범위를 조정합니다.
- 각 단계 시작 시 착수 범위와 의존성을 확인하고, 완료 시 진행표·완료 조건·검증 기록을 갱신합니다.
- 진행 상태는 실제 산출물과 검증 근거로 기록합니다. 구현 완료, 검증 대기, 기존 문제를 구분합니다.
- 규칙 변경, 기존 데이터 호환성 파괴, 무작위 모드 제거, 프로젝트 대이동, 서버·새 언어 도입처럼 범위가 달라지는 결정은 확인을 요청합니다.
- 검증은 변경 영역에 맞춰 수행하며 게임플레이 변경 시 필수 Godot 4개 스위트를 실행합니다. 문서만 변경한 경우에는 문서와 링크를 확인합니다.
- 화면·상호작용 변경은 스크린샷 또는 짧은 영상으로 확인하고 단계 결과에 연결합니다.

단계별 완료 기록에는 아래 항목을 남깁니다.

| 항목 | 기록할 내용 |
|---|---|
| 범위 | 이번 단계에서 완료한 기능과 남긴 기능 |
| 산출물 | 코드·명세·실행 안내·화면 확인 자료 |
| 검증 | 실행 환경, 명령, 결과, 알려진 실패 |
| 판단 | 사용자와 확정한 선택과 이유 |
| 다음 단계 | 착수 조건 충족 여부와 남은 선행 작업 |

## 6. 현재 인계

현재 전체 인수 기준을 완료한 단계는 **1단계**입니다. **2단계의 권장안을 초기 구현 기준으로 채택하고 실제 Electron 앱과 편집·저장·코어 분석의 첫 흐름을 구현했습니다.** 3단계는 현재 Ubuntu에서 샌드박스를 유지한 실행까지 검증했으며 전체 인수는 별도로 판정합니다. 4단계의 생성·고급 제약, 5단계의 확정·게임 반영, 6단계의 운영 전환·플랫폼 검증은 미완료입니다. 구현된 기능과 모호해서 보류한 항목은 [첫 구현 기록](stage_editor_first_build.md)에서 구분합니다.
