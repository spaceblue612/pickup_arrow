# 02. 게임 코어 및 스테이지 분석 요구사항

## 1. 목적

**공용 코어 하나를 게임 플레이와 제작 도구가 함께 사용**해야 한다. 제작 도구에서 생성한 스테이지가 게임에서 다르게 판정되는 일을 방지한다.

확인된 기존 구현: `path_rule.gd`와 `board_state.gd`가 화살의 격자 좌표와 방향으로 경로상의 다른 화살을 확인하고 제거를 처리한다. `Area2D`/Physics 기반 판정이 아니다. 기존 함수·상태 표현은 **실제 코드 확인 전까지 가정하지 않는다**.

## 2. 기능 계층

### A. Rule Runtime — 실제 게임의 유일한 판정자

- 스테이지 초기 상태 구성, 현재 상태 조회.
- 화살의 이동/제거 가능 여부를 기존 규칙에 따라 판정.
- 행동 적용 후 상태 갱신.
- 게임의 클리어 상태 판정.
- UI/애니메이션/씬 노드와의 의존성은 가능한 한 제거하거나 어댑터로 격리.

### B. Stage Validator — 데이터 및 규칙 유효성

- 누락·잘못된 필드, 격자 범위, 화살 위치·방향, 중복/겹침 등 **실제 게임 규칙이 금지하는 조건**을 검사.
- 허용되는 겹침/특수 기믹은 임의로 금지하지 않는다. 실제 코드/데이터 규격에 맞춘다.
- 실패 시 이유 및 가능한 경우 관련 화살 ID·좌표를 반환한다.
- 유효성 통과와 클리어 가능성 통과는 **별도 결과**다.

### C. Stage Solver — 클리어 가능성

- 주어진 게임 상태에서 완료 상태까지 도달 가능한 **합법적인 행동 순서가 존재하는지** 검사.
- 성공 시 실제 규칙을 통과한 풀이 예시/제거 순서 제공.
- 실패 시 가능한 한 막힌 상태나 진행 불가능 원인 제공.
- 계산 자원 제한(상태 수·시간)을 초과하면 `unknown`으로 반환하며 **해결 불가**라고 단정하지 않는다.
- 같은 상태 표현·같은 규칙 함수를 사용하고 중복된 충돌 로직을 만들지 않는다.
- 주의: 화살을 제거해도 다른 선택지가 줄어들지 않는 **단조성**이 실제 규칙에서 증명되는 경우에만 단순 반복 제거(Greedy) 판정으로 충분하다. 그렇지 않거나 향후 기믹이 추가되면 상태 탐색(DFS/BFS 등)과 상태 중복 제거가 필요하다.

### D. Difficulty Evaluator — 난이도 측정

난이도는 단일 수치로 바로 확정하지 않는다. 우선 **설명 가능한 특성 지표**를 수집한다.

- **구조적 특성:** 화살 수, 길이 분포, 격자 점유율, 경로 교차/의존 관계.
- **풀이 특성:** 단계별 제거 가능 화살 수, 병목 구간, 의존성의 깊이, 선택지 변화, 풀이는 얼마나 제약되는지.
- **인지적 특성(추정):** 화면 밀도, 시각적 혼잡, 식별하기 어려운 구조. 이는 실제 유저 난이도와 다를 수 있음을 표시.
- 초기 반환: 지표 값 + 산출 설명 + 임시 점수(선택). 실제 점수/등급 가중치는 플레이 테스트를 통해 조정한다.
- 기존 경험상 **화살 수나 의존성만 많다고 어렵지는 않다**. 한 화살 제거로 연쇄적으로 쉽게 풀리는 스테이지를 과대평가하지 않도록 한다.
- 평가 알고리즘/가중치의 버전을 기록할 수 있게 설계한다.

## 3. 제작 과정에서의 기대 동작

1. 제작 도구가 스테이지 후보 생성 또는 수정.
2. Core Bridge로 데이터 검증 요청.
3. 유효하다면 클리어 가능성 분석.
4. 해결 가능하면 지표/난이도 분석.
5. UI가 통과·오류·풀이 과정·난이도 근거를 표시하고 저장/재생성을 지원.

대량 생성 기능은 추후 동일한 검증 API를 배치 처리하도록 확장한다.

## 4. 최소 요청/응답 형식 — **계약 초안**

현재 스테이지 스키마를 알 수 없으므로 아래 `stage`는 자리표시자다. 기존 저장형식을 우선하고 필요한 경우 어댑터를 만든다.

요청 예시:

```json
{
  "request_id": "example-001",
  "operation": "analyze_stage",
  "stage": {
    "_example": "실제 프로젝트의 기존 스테이지 데이터로 교체"
  }
}
```

응답 예시(모든 필드 확정 아님):

```json
{
  "request_id": "example-001",
  "ok": true,
  "validation": {
    "valid": true,
    "errors": []
  },
  "solver": {
    "status": "solved",
    "solution": ["arrow-id-1", "arrow-id-2"],
    "searched_states": 12
  },
  "difficulty": {
    "metrics": {
      "arrow_count": 2,
      "example_available_moves_at_start": 1
    },
    "score": null,
    "model_version": "unrated-v1"
  }
}
```

- `solver.status`: `solved` / `unsolvable` / `unknown`처럼 명시적으로 구분한다. 검증 실패 및 프로세스 오류는 별도 오류 필드로 취급한다.
- 예시 수치와 화살 ID는 **테스트용 가상 값**이다.
- 최초 구현은 `validate_stage` 하나만으로 시작해도 된다. `analyze_stage` 통합 동작은 이후 추가한다.
- 프로세스 종료 코드·JSON 오류 계약을 정의하고, 잘못된 입력이 게임 엔진을 비정상 종료시키지 않도록 처리한다.

## 5. 최소 테스트 시나리오

- **일치성:** 기존 Godot 게임 플레이에서 가능한/불가능한 제거가 외부 호출에서도 동일하다.
- **유효성:** 정상 맵, 누락 필드, 범위 밖 좌표, 잘못된 방향, 잘못된 화살 ID를 구분한다.
- **해결 가능:** 단순히 완료되는 소형 맵이 실제 풀이 순서와 함께 반환된다.
- **해결 불가:** 현재 규칙에서 진짜 실패하는 테스트 맵이 있다면 `unsolvable`로 반환된다.
- **계산 제한:** 의도적으로 큰/복잡한 맵은 `unknown`으로 안전하게 중단할 수 있다.
- **난이도:** 점수보다 먼저 지표가 재현 가능하게 계산되는지 테스트한다.
- **회귀:** 기존 스테이지의 결과가 코어 변경 후 달라지면 자동 테스트에서 드러난다.

## 6. 구현에서 피할 것

- Electron/Node.js 쪽에 두 번째 충돌·제거 판정 엔진을 만들지 않는다.
- 레벨의 해결 가능성을 정당화 없이 단순 Greedy로 확정하지 않는다.
- 시각적 복잡도를 실제 유저의 체감 난이도와 동일시하지 않는다.
- 코어가 화면/씬 노드를 항상 필요로 하게 만들지 않는다.
- 단계 초기부터 모든 생성·분석 기능을 구현하느라 기본 연동 검증을 미루지 않는다.
