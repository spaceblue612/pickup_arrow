# 03. 단계별 개발 계획 및 검증 기준

> 목표: 기존 게임 개발을 멈추거나 대규모 재구성하지 않으면서 **검증 가능한 작은 단계**로 제작 도구를 분리한다.

## Phase 0 — 기존 프로젝트 조사 (가장 먼저)

**할 일**

1. `project.godot` 위치 및 Godot 버전, 실행/테스트 방법 확인.
2. `path_rule.gd`, `board_state.gd` 실코드·호출부·씬/전역 의존성 파악.
3. 현행 스테이지 생성·저장·로딩 형식 및 스테이지 데이터의 정본 경로 확인.
4. 게임의 합법 행동·클리어 조건·특수 규칙을 코드 근거로 정리.
5. 기존 테스트·Git 상태 확인, 마이그레이션 영향을 받는 참조 목록 작성.

**산출물**: 구조/의존성 조사 결과, 바꿀 파일 후보, 위험 및 누락 정보. **확인하지 않은 사실을 임의로 가정하지 않는다.**

**완료 기준**: 현재 코어가 화면 없이 실행 가능한지 판단하고 최소 변경 계획을 도출했다.

## Phase 1 — 기존 규칙 코어의 CLI 호출 성공 (최우선 MVP)

**할 일**

1. 가능하면 기존 두 파일을 이동하지 않고 GDScript 브리지 추가.
2. JSON 요청 파일 1개 입력, 판정/오류 JSON 1개 출력, 종료 코드를 정의.
3. 기존 룰을 통해 간단한 화살 행동 또는 스테이지 유효성 검사 1개 수행.
4. 호출 예시 명령 또는 실행 스크립트 추가.
5. 게임 내 기존 동작과 headless 결과가 동일한지 테스트.

**완료 기준**: UI 없이 Godot CLI 한 번 실행으로 JSON 검증 결과를 얻고, 기존 게임이 정상 동작한다.

**이 단계가 완료되기 전에는 Electron UI/대규모 Solver/난이도 기능을 한꺼번에 구현하지 않는다.**

## Phase 2 — 최소 Electron 데스크톱 제작 도구

**할 일**

1. Electron + React + TypeScript 프로젝트 기본 구성.
2. UI에서 스테이지 파일 선택, 요청 실행, JSON 응답/오류 표시.
3. Electron `main`에서 Node.js 프로세스로 Godot headless 호출.
4. `preload`를 통한 제한된 IPC API를 제공하고 렌더러에는 Node 권한을 직접 부여하지 않음.
5. Windows/Ubuntu/macOS를 고려한 경로 설정. 우선 주 개발 OS에서 정상 작동 확인.

**완료 기준**: 데스크톱 앱에서 버튼을 누르면 기존 Godot 코어 분석이 실행되고 결과가 표시된다.

## Phase 3 — 코어 분석 기능

**할 일**

1. `StageValidator`의 구조 및 규칙 유효성 검사.
2. `StageSolver`의 풀이 탐색, 한계 도달 시 `unknown` 구분.
3. `DifficultyEvaluator`의 지표(초기 점수식은 보류 가능).
4. 단위/회귀 테스트 및 소형 맵 기준 샘플 세트.
5. 게임 런타임과 도구 분석 코드의 의존성 분리/내보내기 검토.

**완료 기준**: 정상/실패/불확실 케이스를 구분하고 근거 있는 분석 결과를 JSON으로 제공한다.

## Phase 4 — 실제 편집·맵 생성 UI

**할 일**

1. 큰 작업 공간, 줌/팬, 화살 생성·이동·삭제 및 속성 편집.
2. 사용자 요청에 맞는 맵 생성 옵션·알고리즘 추가.
3. 생성 → 검증 → 결과 필터링 → 저장·게임 반영 흐름.
4. 풀이 순서 재생, 방해 관계 표시, 난이도 지표 시각화.
5. 대량 생성이 필요해지면 배치 호출 또는 상시 실행 프로세스로 최적화.

**완료 기준**: 제작 도구가 기존 Godot 편집 씬을 대체할 수 있고 게임을 열지 않고도 후보 생성·검증이 가능하다.

## Phase 5 — 크로스플랫폼 안정화 및 배포

**할 일**

- 실제 Windows / Ubuntu / macOS에서 개발 실행·경로·인코딩·Godot 호출 검증.
- 앱별 설정, 스테이지 저장 경로, Git 동기화 동작 점검.
- 필요하다면 Electron Forge 등으로 OS별 패키징.
- Godot 설치 의존성을 유지할지 번들할지 선택.
- macOS 서명·공증 등 배포 요구 사항 확인.

**완료 기준**: 세 운영체제에서 동일한 맵 데이터와 규칙 결과를 재현할 수 있다.

## 작업 규율

- **작은 커밋/작은 변경:** 실행 가능한 상태를 유지.
- **원본 보존:** 기존 게임 화면과 스테이지 재생 기능을 먼저 보호.
- **증거 우선:** 구조/규칙은 파일과 호출 관계를 확인하고 설명.
- **경계 분리:** Node.js 생성 알고리즘은 후보 생성만, 규칙의 최종 판단은 Godot 코어만.
- **승인 지점:** 폴더 대이동, 스테이지 포맷 호환성 파괴, 엔진 버전 변경, 새로운 서버 도입, 규칙 재작성 등은 선행 조사 결과와 이유부터 제시.
- **검증 기록:** 실행 명령, 통과/실패 테스트, 남은 위험과 다음 작업을 작업 종료 시 정리.
