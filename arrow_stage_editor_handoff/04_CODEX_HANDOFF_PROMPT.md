# Codex 작업 전달 프롬프트 — Arrow Stage Editor 아키텍처 전환

다음은 기존 Godot 화살뽑기 게임 저장소를 열어둔 상태에서 Codex에 전달할 작업 지시다.

---

## 역할과 목표

당신은 기존 Godot 게임을 유지하며 **Electron 기반 독립 데스크톱 스테이지 제작 도구**를 도입하는 개발 담당자다. 새로운 시스템을 한꺼번에 완성하는 것이 아니라, 기존 게임 규칙을 단일 코어로 활용할 수 있도록 단계적으로 개선한다.

우선 이 저장소의 `docs/arrow_stage_editor_handoff/README.md`(전달 패키지 안내), `docs/arrow_stage_editor_handoff/01_ARCHITECTURE.md`, `docs/arrow_stage_editor_handoff/02_CORE_REQUIREMENTS.md`, `docs/arrow_stage_editor_handoff/03_IMPLEMENTATION_ROADMAP.md`를 읽고, 이 문서들을 현재 저장소와 대조하라. 문서 파일이 다른 경로에 복사되어 있다면 해당 위치에서 읽어라. 이 문서들은 **기존 코드를 확인하기 전의 설계안**이며 실제 구현보다 우선하는 가상의 사실이 아니다.

## 설계 결정 (기본적으로 유지)

- Git Monorepo 하나에서 게임과 제작 도구를 관리한다.
- 게임: **Godot + GDScript** 유지.
- 제작 도구: **Electron + React + TypeScript + Electron 내장 Node.js**, 독립 데스크톱 앱.
- 대상 OS: Windows / Ubuntu(Linux) / macOS.
- 별도 HTTP 서버·별도 Python 코어·C# 재작성은 초기 도입하지 않는다.
- **공용 게임 규칙은 Godot 프로젝트 내부**에 단 하나만 존재한다.
- 제작 도구는 Node.js로 후보를 생성하거나 파일을 다룰 수 있지만 충돌/제거 규칙의 최종 판정은 Godot 코어가 한다.
- Godot를 `--headless`로 호출하고 JSON 요청/응답을 교환한다. 초기에는 **요청당 실행 + JSON 파일 I/O**로 시작한다.
- 코어 책임: 실제 룰, 스테이지 유효성, 클리어 가능성, 난이도 측정. 실게임에 필요한 런타임과 제작 도구용 분석은 구분한다.

## 기존 프로젝트에 대해 이미 확인된 사항

- 기존 룰 코드 파일명: `path_rule.gd`, `board_state.gd`.
- 기존 화살 판정은 `Area2D`/Physics가 아닌 **격자 좌표와 방향의 GDScript 계산**으로 진행 경로의 다른 화살 여부를 판정하고 제거한다.
- 과거에는 Godot 씬 전환으로 게임과 제작 도구를 오갔는데 게임 창(모바일/소형)과 제작 도구(넓은 화면/다양한 옵션)의 UI 요구가 달라 창 크기·레이아웃 문제로 불필요한 시간이 들었다.
- 현재 스테이지 데이터 구조, 파일 경로, UI/씬과 코어의 실제 결합 정도는 **소스 조사 전까지 미확인**이다.

## 이번 1차 작업의 범위: Phase 0 + 가능한 범위의 Phase 1만

1. **먼저 조사:** 저장소 구조, `project.godot` 위치 및 버전, 기존 룰 함수, 관련 호출부, 씬/전역 상태 의존성, 스테이지 파일 형식, 현재 실행·테스트 방법을 파악하라.
2. **최소 분리안:** 현재 경로를 최대한 유지하면서 화면 없는 코어 실행이 가능하도록 필요한 최소 변경을 제안하라. 실제 종속성이 없다면 이동 자체를 하지 않아도 된다.
3. **기본 CLI 연결:** 가능한 경우 `cli_runner.gd` 같은 작은 브리지를 구현해 JSON 파일 입력 하나를 받아 현재 룰로 검증/판정하고 JSON 파일 결과를 출력하도록 하라. 실제 데이터 구조를 분석한 후 스키마를 정한다.
4. **검증:** Godot 게임의 기존 동작이 유지되는지 확인하고, 헤드리스 판정과 게임 내 결과를 비교하는 최소 테스트를 실행하라. 테스트가 없는 경우 재현 가능한 검사 절차를 제공하라.
5. **보고:** 확인된 사실, 변경 파일, 실행 명령, 검증 결과, 남은 이슈, 다음 Phase 2 착수 조건을 간결히 정리하라.

### 절대 피할 것

- 실제 파일을 읽기 전에 `path_rule.gd`/`board_state.gd` 내부 함수·데이터 구조를 지어내지 말 것.
- 처음부터 React UI, 완성형 Solver, 난이도 점수, 패키징까지 동시에 구현하지 말 것.
- 두 번째 충돌/제거 룰 엔진을 TypeScript 또는 Python으로 작성하지 말 것.
- 기존 게임 프로젝트 디렉터리를 무조건 재배치하거나 대규모 리팩터링하지 말 것.
- 기존 스테이지 데이터를 호환성 확인 없이 새 JSON 스키마로 교체하지 말 것.
- `unknown`(계산 한계)과 `unsolvable`(해결 불가능)을 혼동하지 말 것.
- 도구 UI에서 Node 전체 권한을 직접 사용할 수 있게 설정하지 말 것(이후 Electron 도입 시).

## 다음 단계에서 유지할 방향(이번에 모두 구현할 필요 없음)

- Electron `renderer(React)` ↔ `preload(제한된 IPC)` ↔ `main(Node.js)` ↔ `Godot headless core`.
- `StageValidator`: 데이터·룰 유효성.
- `StageSolver`: 실제 코어를 활용한 해결 경로 확인. 규칙의 단조성 검증 없이 Greedy만으로 해결 가능성을 결론내지 말 것.
- `DifficultyEvaluator`: 구조적/풀이/인지적 특성 지표부터, 체감 난이도 점수는 추후 조정.
- Windows / Linux / macOS 플랫폼별 Godot 경로는 앱 로컬 설정으로 분리.

## 작업 방식

- 원래 게임의 정상 동작 보존을 최우선으로 한다.
- 구현이 가능하면 Phase 1까지 진행하되, 핵심 의존성·규칙이 불명확하거나 파괴적 변경이 필요하면 **조사 결과와 구체적 최소 변경안까지 먼저 보고**하라.
- 설계 개선을 제안할 수 있지만 확정 사항과 제안 사항을 분리한다.
- 단계별 완료 조건을 충족하는지 결과 중심으로 판단한다.

## 최종 응답 형식

1. **현황:** 발견한 코드·의존성·실제 파일 경로.
2. **수행:** 수정한 파일과 변경 의도(또는 수정 전 제안 사항).
3. **검증:** 사용한 명령, 성공/실패, 기존 게임 호환성.
4. **다음 작업:** Phase 2 착수에 필요한 가장 작은 한 가지 작업.

---

**최종 목표:** 넓은 작업 공간을 가진 별도 데스크톱 제작 도구로 스테이지를 생성·분석하고, 실제 게임과 제작 도구가 **같은 Godot 코어 규칙**을 사용하도록 한다. 하지만 이번 지시는 전체 구현이 아니라 **코어의 외부 호출을 먼저 검증하는 첫 이행 단계**다.
