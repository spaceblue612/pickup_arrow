# 화살뽑기 게임·스테이지 제작 도구 — Codex 전달 패키지

> 작성 기준: 2026-10-19 대화에서 합의한 설계. 실제 소스코드는 아직 검사하지 않았으므로 경로·API·데이터 형식은 **안(案)**이며, 기존 프로젝트를 우선한다.

## 이 작업을 시작한 이유

현재 화살뽑기 게임은 Godot로 개발 중이다. 맵 생성·편집 도구까지 Godot 씬으로 구현하고 씬 전환으로 게임과 도구를 오가려 했으나 다음 문제가 발생했다.

- 게임 화면은 모바일 또는 작은 화면 비율인 반면 도구는 큰 작업 공간·많은 옵션·다수의 패널이 필요하다.
- 씬만 전환해서는 실행 창 크기·UI 배치를 작업 방식에 맞게 자연스럽게 전환하기 어려웠다.
- 화면 크기와 배치 문제를 고치느라 실제 맵 제작 기능에 쓸 시간이 낭비되었다.
- 따라서 도구 UI와 게임 UI는 분리하고, **규칙만 하나로 공유**한다.

중요한 선행 사실: 기존 `path_rule.gd`와 `board_state.gd`는 `Area2D`/Physics 충돌에 의존하지 않으며, 화살의 **격자 좌표와 방향을 GDScript로 직접 계산**하여 경로의 장애물·제거를 판정한다. 이 코드를 최대한 재사용하는 것이 목표다.

## 합의된 핵심 결정

1. **Git 저장소 하나(Monorepo)**에 게임과 제작 도구를 함께 둔다.
2. **게임은 Godot + GDScript**를 계속 쓴다.
3. **공용 규칙 코어는 Godot 프로젝트 내부**에 둔다. 게임 UI와 제작 도구가 같은 코어를 사용하고, 중복 규칙을 만들지 않는다.
4. 제작 도구는 **Electron + React + TypeScript + 내장 Node.js**로 만든 **독립 데스크톱 앱**이다. 브라우저 웹서비스/별도 백엔드 서버가 아니다.
5. 대상 OS는 **Windows / Ubuntu(Linux) / macOS**다. 하나의 소스코드를 유지하되 설치·실행 경로 및 배포 파일은 OS별로 처리한다.
6. 제작 도구는 필요할 때 **Godot headless CLI 실행**으로 코어에 요청하고 JSON 파일로 결과를 받는다. 초기에는 요청당 실행하는 가장 단순한 형태로 시작한다.
7. 코어는 **규칙 유효성 검증, 클리어 가능성 판정, 난이도 평가**를 제공해야 한다. 실제 게임 런타임과 무거운 분석 기능은 논리적으로 분리한다.
8. 초기에는 **Python, C# 재작성, 별도 서버, 자동 패키징 파이프라인**을 추가하지 않는다. 필요할 때 검토한다.

## 전달 방법

Codex에서 **기존 Godot 저장소를 열고**, 이 폴더 전체를 저장소의 `docs/arrow_stage_editor_handoff/`로 복사한다. (기존 `docs/README.md`가 있다면 덮어쓰지 않는다.) 그다음 `04_CODEX_HANDOFF_PROMPT.md` 전체를 첫 지시로 전달한다.

**유의:** 실제 저장소 구조가 아래 문서의 예시와 다르면 기계적으로 폴더를 이동하지 말 것. 기존 코드 확인 → 의존성 목록 작성 → 최소 변경안을 제안/검증 → 단계별 이행 순서로 진행한다.

## 아직 확정하지 않은 것

- 현재 프로젝트의 실제 디렉터리 구조, Godot 버전, 저장 중인 스테이지 파일 형식.
- `board_state.gd`가 `Node`, `Resource`, autoload, 씬 노드 등 어떤 것에 의존하는지.
- 화살 제거 후 상태가 단조적으로 단순해지는지(예: 제거가 다른 화살의 이동 가능성을 줄이지 않는지).
- 난이도의 구체 점수식과 등급 기준. 초기에는 **측정 지표 및 설명 가능 결과**부터 구현한다.
- 제작 도구의 상세 화면 설계, 자동 생성 알고리즘의 상세 옵션, 배포/설치 자동화.
